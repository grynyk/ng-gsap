ng-gsap — handoff notes
========================
Written: 2026-08-14
For: the next engineer picking this repo up

WHAT THIS IS
------------
A signals-first Angular wrapper for GSAP, in the spirit of @gsap/react. Angular
CLI workspace with two projects:

  projects/ng-gsap    the publishable library (npm name: "ng-gsap")
                       + two secondary entry points: ng-gsap/scroll-trigger,
                       ng-gsap/testing
  projects/playground  zoneless demo app, one live example per feature

Package manager is Yarn Berry (via corepack), node-modules linker (Angular
tooling doesn't support PnP). Do not switch to npm/pnpm without a reason —
that was a deliberate choice, not a default.

The core idea, in one line: @gsap/react's useGSAP takes a manual dependency
array like useEffect. Angular doesn't need one — injectGSAP() runs its
callback inside a render effect, so any signal read inside it becomes a live
dependency automatically. Everything else in the library (directives,
gsapScrub, injectScrollTrigger) leans on the same pattern: signal in, signal
out, no NgZone juggling.

CURRENT STATE (what's actually finished)
-----------------------------------------
- Core library: provideGsap, injectGSAP (+ contextSafe), animationSignals,
  gsapScrub, GSAP_CONFIG/GSAP_TIMELINE tokens.
- Directives: gsapTo, gsapFrom, gsapFromTo (all three DI-compose into a parent
  gsapTimeline automatically), gsapHover/gsapHoverLeave, gsapTimeline.
- ng-gsap/scroll-trigger: injectScrollTrigger (progress/isActive/direction as
  signals).
- ng-gsap/testing: provideGsapTesting + tickGsap, drives gsap's ticker off a
  fake clock for deterministic tests. This one's actually verified to work
  (see tests) — I was skeptical GSAP's internal ticker would cooperate with
  vitest fake timers, wrote a real test for it, and it passed.
- 18 passing unit tests across both entry points (Vitest, jsdom). They test
  real behavior, not mocks — e.g. the DI timeline composition test asserts
  actual tween.parent identity, not just "didn't throw."
- Playground: 7 examples + home, dark theme, code snippets alongside each
  live demo. Manually driven end-to-end with Playwright in this session
  (screenshots + interaction assertions) — everything works, zero console
  errors. That verification script was NOT committed to the repo (it lived in
  a scratch dir); see "Testing gaps" below.
- GitHub Actions: ci.yml (build + test on push/PR), release.yml (publish on
  v*.*.* tags, needs NPM_TOKEN secret), pages.yml (deploy playground to GH
  Pages on push to main, includes the 404.html SPA-fallback trick).
- README (root + package), MIT LICENSE.

TESTING GAPS TO CLOSE
-----------------------
- injectScrollTrigger's unit test is a light smoke test only. jsdom has no
  real layout (getBoundingClientRect returns zeros), so ScrollTrigger's
  actual start/end/scrub math is essentially unverified by unit tests.
  Consider a Playwright-based test for this specifically, since it needs
  real scroll/layout behavior.
- The playground has almost no automated tests — just a fixed-up version of
  the Angular-CLI-generated placeholder spec (projects/playground/src/app/app.spec.ts,
  now actually passing and checking the nav renders one link per example).
  `ng test playground` is not wired into CI yet; only the library is.
- Turn the manual Playwright walkthrough from this session into a real
  checked-in e2e suite (a `e2e/` folder, wired into ci.yml). The script
  itself is disposable, but the pattern it used — navigate to each route,
  assert real state changes (bounding boxes, computed styles, element
  counts), check console errors — is worth keeping permanently rather than
  re-deriving by hand next time.
- No test yet against a real Angular 21 install specifically — peerDeps say
  ">=21.0.0" but everything so far has only run against 22.1.x locally.
- No SSR/hydration smoke test. injectGSAP is designed to no-op on the server
  (afterRenderEffect doesn't run there), but that's reasoned from Angular's
  docs, not verified against an actual @angular/ssr app.

HYGIENE / PROCESS GAPS
------------------------
- No linting. There's no @angular-eslint set up — I started to add a "lint"
  script pointing at `ng lint` but ripped it back out (from both
  package.json and ci.yml) because there's no lint builder actually
  configured, and a broken CI step is worse than no CI step. Wiring up
  @angular-eslint + Prettier-in-CI is a quick, high-value follow-up.
- No changelog / version-bump automation. release.yml just publishes
  whatever version happens to be in projects/ng-gsap/package.json when a tag
  lands — nothing bumps it or generates release notes. For a single-package
  repo, Changesets is a good fit; worth adding before this gets real
  contributors.
- No CONTRIBUTING.md, issue templates, or CODEOWNERS.
- Version is 0.1.0 — pre-1.0, API should be treated as unstable. No
  documented commitment yet on what "1.0" requires.

DESIGN DECISIONS WORTH KNOWING ABOUT (so you don't re-litigate them blind)
-----------------------------------------------------------------------------
- gsap is a peerDependency everywhere, never bundled — this mirrors
  @gsap/react and matters because of GSAP's licensing (paid plugins require
  the consumer's own install/registry auth). The playground's SVG example
  deliberately avoids DrawSVGPlugin (a paid bonus plugin) and uses the
  classic free-tier stroke-dasharray/dashoffset trick instead. Keep this
  constraint in mind before adding examples that lean on bonus plugins
  (DrawSVGPlugin, MorphSVGPlugin, etc.) — they'd break for anyone without a
  GSAP Business license.
- Directives are standalone-only, no NgModule support. Deliberate, given the
  Angular 21+ target — flagging it as a conscious scope decision, not an
  oversight, in case someone asks for NgModule compat later.
- gsapScrub avoids an infinite feedback loop (signal write -> seek timeline
  -> onUpdate -> signal write -> ...) via an epsilon-diff comparison rather
  than a boolean "syncing" flag. A flag doesn't work because effect() flushes
  asynchronously, so a synchronously-reset flag is already false by the time
  the effect body runs. The epsilon approach works because effect flush
  happens same-tick, before the timeline's progress can have drifted. This
  is subtle — if you touch gsap-scrub.ts, keep the reasoning (and the
  EPSILON comment) intact, and add a regression test if you change it.
- gsapTimeline's DI composition relies on Angular's render-phase ordering:
  child directives add themselves to the shared timeline in the `write`
  phase; the parent plays the timeline via `afterNextRender`'s default
  `mixedReadWrite` phase, which always runs after `write` in the same render
  pass — regardless of where in the component tree each child sits. This is
  the mechanism that makes the DI composition example actually work; it's
  documented in the directive's docstring, but worth internalizing before
  changing the timing of either side.
- Package name is unscoped "ng-gsap" (not "@danielgrynyk/ng-gsap" or the
  originally-requested "ngx-gsap", which was already taken by an unrelated
  package on npm). If that ever needs revisiting, it was a deliberate choice
  made with the repo owner, not a default.

IDEAS FOR MAKING THIS ACTUALLY KILLER-COOL (roughly sequenced)
-------------------------------------------------------------------
These are genuine differentiators against @gsap/react, not just parity
features — pick based on what would actually move adoption.

Near-term, highest leverage:
  - `ng add ng-gsap` schematic: scaffold provideGsap() into app.config.ts
    automatically. This is the single biggest DX unlock for adoption — most
    Angular library success stories (Material, PWA) lean hard on `ng add`.
  - `provideGsap({ respectReducedMotion: true })`: wrap GSAP's own
    gsap.matchMedia() to globally respect prefers-reduced-motion. Currently
    nothing in this library thinks about accessibility/motion sensitivity at
    all — that's a real gap for a production-grade animation library, not
    just a nice-to-have.
  - A checked-in e2e suite (see Testing gaps above) — unlocks confidently
    shipping the next two ideas without regressing the first ones.

Medium-term, genuine differentiation:
  - provideGsapRouteTransitions(): hook into Angular Router's navigation
    lifecycle to run enter/leave animations on route change. Angular's
    router DI/lifecycle hooks could make this meaningfully cleaner than
    React's route-transition ecosystem — this is the strongest "why Angular,
    why not just use @gsap/react" pitch available. Consider it as its own
    secondary entry point (ng-gsap/router), same pattern as scroll-trigger,
    so router stays an optional peer.
  - gsapFlip(): wrap GSAP's Flip plugin (free tier) for animated list
    reordering / shared-element transitions, aimed at Angular's @for/track.
    Big demo potential for the playground.
  - gsapMediaQuery()/breakpoint signal: expose GSAP's own matchMedia() as a
    signal for conditional template logic tied to animation breakpoints.

Longer-term / polish:
  - Hosted docs site once the API stabilizes (the README table is fine for
    now, won't scale past ~15 exports).
  - A small debug overlay (in the playground, maybe opt-in in the library)
    listing active gsap.context()s/timelines — genuinely useful for anyone
    debugging leaks, and good marketing for the "everything auto-cleans-up"
    story.
  - Validate against a real Angular 21 install (see Testing gaps) before
    claiming that peerDependency floor with confidence.

WHERE TO START
---------------
Read projects/ng-gsap/README.md first (it's the actual npm package
description) and projects/ng-gsap/src/lib/inject-gsap.ts second (it's the
one piece of code everything else in the library either uses or mirrors the
pattern of). Then walk the playground locally (yarn build:lib && yarn start)
before changing anything — it's the fastest way to build an accurate mental
model of what already works.
